# Очередь писем: локальный этап

Ветка `feature/production-hardening`, продолжение локальных изменений после проверки
из HARDENING_LOCAL_RESULT_2026-09-08.md. Изменения не отправлены в remote.

## Реализация

- EmailOutbox в PostgreSQL: отдельное задание на получателя, уникальный ключ события,
  состояния pending/processing/sent/failed/cancelled, счётчик попыток и сроки.
- Письма сохраняются в транзакциях создания/отмены записи и создания аккаунта.
  Ошибка постановки откатывает соответствующую бизнес-операцию.
- В очередь переведены клиентские и станционные уведомления, напоминания,
  ссылки установки пароля и приветствия операторов. HTTP-запросы не вызывают SMTP.
- Отправитель process_email_queue использует короткую транзакцию SKIP LOCKED
  и lease на 5 минут. SMTP выполняется вне транзакции и блокировок Appointment.
- До 8 попыток, задержка начинается с 30 секунд и удваивается до часового предела.
  Потерявший lease обработчик не может переписать результат нового обработчика.
- Перед отправкой проверяются актуальность записи, её версия, адрес получателя,
  права/предпочтения сотрудника, состояние аккаунта и токен установки пароля.
- Версия записи меняется при переносе: возврат на прежнее время не переиспользует
  старое отменённое/отправленное напоминание. reminder_sent_at означает успешное
  принятие backend, а не постановку в очередь.
- Админка системного администратора показывает только метаданные очереди;
  можно повторить failed. Тела писем и токены не показываются.
- purge_email_queue удаляет sent/cancelled старше заданного срока (по умолчанию 30 дней).
  Pending/processing/failed сохраняются. Автоматический запуск очистки на сервере
  описан в README, локально он не настраивался.
- Compose получил сервис mail. Backup/restore учитывает его остановку и возобновление.
  Smoke test проверяет восстановление ожидающего письма вместе с записью и PNG-фото.

Миграции: 0027_email_outbox и 0028_email_schedule_revision.

## Границы гарантий

SMTP не даёт атомарного подтверждения вместе с PostgreSQL: при аварии после принятия
письма SMTP и до сохранения результата возможен повтор. Message-ID при повторе
сохраняется, но это не гарантия удаления дублей получателем. То же ограничение
действует после восстановления старой резервной копии. Проверка актуальности
выполняется перед отправкой и не может отозвать уже начатую SMTP-передачу.

Тела писем и ссылки паролей хранятся в БД до очистки; срок хранения также определяет
окно дедупликации событий. Локальные проверки не отправляют внешних писем:
используются locmem/console backend и контролируемые сбои SMTP.

## Подготовленное локальное окружение

Сайт: http://localhost:8001. В текущем локальном окружении используется console
backend. SMTP-секреты пользователя не менялись. Рабочие deployment вне созданного
нами `sto-hardening-*` окружения не изменялись.

Запуск существующих контейнеров после остановки:

```powershell
docker compose --env-file .env.local -p sto-hardening-local up -d db redis
docker start sto-hardening-web sto-hardening-mail
```

Просмотр сообщений обработчика (console backend выводит также само письмо):

```powershell
docker logs --tail 100 sto-hardening-mail
```

Остановка с сохранением данных:

```powershell
docker stop sto-hardening-web sto-hardening-mail
docker compose --env-file .env.local -p sto-hardening-local stop db redis
```

Обработчик создан из образа `sto-email-queue:local`; при дальнейших изменениях кода
его нужно пересобрать и пересоздать. Запуск production-сервиса `mail` описан в README.
